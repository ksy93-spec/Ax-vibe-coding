# 작업 절차

## 한 세션 = 한 킷

세션을 열 때마다 "이번에 만들 도구 하나"를 정합니다. 여러 도구를 한 세션에서 다루면
산출물이 섞이고, 나중에 어떤 파일이 어느 킷 소속인지 추적이 안 됩니다.

## 1단계. 명세 (바깥)

내가 만드는 것:

- `specs/<이름>.md` — 입력, 출력, 화면, 예외 상황, 하지 않을 것
- 타입 정의 파일 (`.d.ts` 또는 Python `Protocol`/dataclass)
- 합격 기준. 가능하면 실패하는 테스트로, 어려우면 체크리스트로.

명세 단계에서 시간을 쓰는 게 전체 품질을 가장 크게 바꿉니다.
사내 모델이 무너지는 지점은 지식 부족이 아니라 긴 작업 중 목표가 흐려지는 것이라서,
목표를 파일로 고정해두면 그 실패가 대부분 사라집니다.

## 2단계. 스캐폴드 (바깥)

- 의존성을 실제로 설치하고 실행해 확인
- 폰트, 아이콘, 디자인 토큰을 파일로 확보
- 껍데기까지 동작하는 상태로 만들기. 비즈니스 로직은 `TODO(사내)` 주석으로 비워둡니다.
- `MANIFEST.md`와 `OFFLINE.md` 작성

## 3단계. 프롬프트 팩 (바깥)

킷 안의 `PROMPT.md`에 사내에서 그대로 붙여넣을 지시문을 씁니다.
Qwen-Cline용과 ChatGPT Enterprise용을 나눠 쓰는 게 좋습니다.
Cline은 파일을 직접 고치므로 파일 경로와 수정 범위를 못박아야 하고,
ChatGPT Enterprise는 파일을 못 보므로 필요한 코드를 프롬프트에 함께 넣어야 합니다.

## 4단계. 반입

`scripts/pack.sh <킷이름>` 으로 압축합니다. 반입 전에 `docs/intake-checklist.md`를 훑습니다.

## 5단계. 되돌아오기

사내에서 막히면 다시 바깥으로 가져옵니다. 가져올 때는 사내 식별 정보를 지우고
에러 메시지와 최소 재현 코드만 남깁니다. 그 내용으로 `specs/`를 고치고 킷을 개정합니다.
같은 문제가 두 번 나오면 명세가 부족했던 겁니다. 코드만 고치지 말고 명세를 고칩니다.

## 사내 모델별 쓰는 법

### Qwen 3.5-Cline (VS Code)

강점은 파일을 직접 읽고 고친다는 점, 약점은 컨텍스트가 길어질수록 엉뚱한 파일을 건드린다는 점입니다.

- 한 요청에 한 파일. "이 파일만 고쳐, 다른 파일은 열지 마"를 명시합니다.
- 작업 전 `.clinerules`에 킷의 금지 사항을 넣어둡니다. 매번 프롬프트에 쓰는 것보다 잘 지켜집니다.
- 리팩터링을 시키지 말고 "이 함수의 본문을 채워라" 수준으로 쪼갭니다.
- 자동 승인은 끄고 diff를 확인합니다. 이 모델은 멀쩡한 코드를 조용히 지우는 일이 있습니다.

### ChatGPT Enterprise

강점은 설계 대화와 긴 텍스트 처리, 약점은 저장소 상태를 모른다는 점입니다.

- 코드를 붙여넣을 때 파일 경로를 주석으로 첫 줄에 넣습니다.
- 출력은 전체 파일로 받습니다. 부분 diff를 받으면 적용하다가 깨집니다.
- 정규식, SQL, 엑셀 수식, 데이터 변환 같은 단발성 작업에 쓰는 게 효율이 좋습니다.
- 프로젝트 기능이 있으면 킷의 `specs/`와 타입 정의를 지식 파일로 올려두고 씁니다.
